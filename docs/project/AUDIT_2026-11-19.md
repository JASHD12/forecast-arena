## A. Executive assessment

**Technical state: good, and better than at the last review.** All seven forecasters run
live on four domains: power, weather, Wikipedia attention and markets. The ML forecaster
has been live since the 16 November batch. Each batch since then has 33 of 33 `ml`
forecasts, from registered champions (power HGB `power-gbq-r1-2026-11-12`, attention
LightGBM `attention-lgbc-r1-2026-11-07`, weather rules r2, markets EWMA r1), and every
forecast carries its artifact SHA-256.

The health checks for the latest scheduled runs all pass, ledger verify passes (208 files,
7 seals), and the 17 and 18 November days count as clean.

The answer to the owner's earlier question, "why are the ML models not working?", is
therefore: they were not wired into the daily job until T193 (commit 5cfebf0, 15 November).
Since 16 November they are live.

**Biggest operational risk: GitHub's scheduler.**
- Scheduled morning runs start between 07:24 and 07:53 UTC for a 00:15 slot, about 1.5
  hours before the 09:30 lock.
- Evening runs start between 22:52 and 04:00, so some batches miss the "publish the night
  before" questions (11-17 fell back to v1).
- Scheduled players runs start between 17:31 and 19:37, which is always after the lock,
  so they can never do their work.

**Presentation state: honest, but it does not land in 10 seconds.**
- The home hero ranks "ML model 0.117" first without saying it rests on 24 questions over
  3 days.
- The recruiter page has the candidate's name, but no degree, availability, contact or CV,
  and it carries the public placeholder "Personal contributions and recruitment details
  require owner confirmation."
- The README opens with a keyword wall.

**Five highest-impact actions**

   not advertise players or evening questions as reliable. *Owner action plus small code
   changes (R1, R2).*

   - "starts automatically after five clean days" ignores the owner's not-before date

   one verified result, contact and CV, and two evidence links (P1 and P2).
4. **Rewrite the README opening** to lead with the question, the 0.193 vs 0.221 backtest,

5. **Ship the two analyses an interviewer will ask for** (C1 and C2):
   - a slice table of backtest Brier by template, season, holiday and negative-price days;

## C. Findings

Operational severity runs from S1 (integrity or correctness) to S4 (cosmetic). Hiring
priority runs from H-high to H-low.

**F1 · Scheduler · S2 / H-low · GitHub cron is too late for the lock-critical and
evening work**
- **Evidence:**
  - morning 44479336328 started 07:24 for a 00:15 slot; 44258928718 started 07:26;
    44042172548 started 07:53;
  - evening 43984332556 started 00:02, so batch 11-17 got v1 questions;
  - players 44359638225, 44363683181 and 44365972714 started 17:31 to 18:06.
- **Root cause:** GitHub's scheduler delay on this repository, about 6 to 9 hours. The
  code is correct: the gates refuse late work.
- **Resolution:**
  - owner: H20, an external `workflow_dispatch` caller;
  - code:
    - R1, document and test the dispatch-only path;
    - R2, show the players feature as "manual only" until runs land inside the window.
- **Acceptance:** for 7 consecutive days the morning seal lands before 08:30 and the
  evening v2 questions before 23:59 on B-1. Measure from `runs/` manifests.

**F2 · Wording · S2 / H-med · "The official record starts automatically after five clean
days" omits the not-before gate**
- **Where:** `src/arena/site/templates/findings.html:5`, `leaderboard.html:10`,
  `guide.html:50`, `base.html:29` (tooltip). `methods.html:39` is correct.
- **Expected vs actual:** with not-before 2099-12-31 the record never starts. A reader
  told it is "automatic" will expect it soon.
- **Resolution:**
  - one shared macro: "Starts after five clean days in a row and not before the owner's
    pre-registered date (not yet set)";
  - show the clean-day count, computed by `official.day_statuses`, on Status.
- **Test:** a site unit test asserts the macro text when `official_start` is None and
  not-before is unset or in the future.

**F3 · Presentation · S3 / H-high · Home standings hide sample size**
- **Where:** `src/arena/site/templates/index.html:22`. The common board has n=24
  questions over 3 days. The leaderboard says so; the home page does not.
- **Resolution:**
  - render `{{ board.questions }} questions · {{ board.days }} days` beside the label;
  - when the label is "too early to tell", lighten the ranks visually (still ranked, but
    grey numbers).
- **Test:** home render test asserts the n and days text.

**F4 · Layout · S3 / H-med · Leaderboard overflows the page at every width**
- **Trigger:** open `leaderboard.html` at 390 px or 1366 px; document `scrollWidth` is
  1439 or 1546.
- **Cause (hypothesis):** `.table-scroll` (`style.css:142`) sits in a grid or flex child
  without `min-width: 0` or `max-width: 100%`, so the `table.heatmap.h2h` and participation
  tables widen the page instead of scrolling inside it.
- **Resolution:** CSS fix, then add a Playwright check to `make a11y` that every built
  page has `scrollWidth <= innerWidth` at 390 and 1366 px.

**F5 · Content · S3 / H-high · Recruiter page shows an unfinished placeholder in public**
- **Where:** `recruiters.html:8`: "Personal contributions and recruitment details require
  owner confirmation."
- **Resolution:**
  - until H16 is done, replace the sentence with the neutral authorship line ("Specified
    and directed by Jashdeep Singh; implemented with AI coding agents; every figure is
    generated from the public record");
  - after H16, add the facts.
- Never invent degree, university or availability.

**F6 · Presentation · S3 / H-med · The README image is the fixture demo, not the live
site**
- **Where:** `README.md` line 22: "*Screenshot of the offline demo build (fixture
  data)*".
- **Resolution:** a script regenerates `docs/img/home.png` from a site built on a ledger
  snapshot (dated caption), run by hand. CI cannot reach the live ledger state
  reproducibly, so keep this out of `make check`.

**F7 · API · S4 / H-low · `api/v1/leaderboard.json` rows omit ML and the LLMs**
- **Cause:** the rows come from the ALL board, which requires coverage of every
  base_rate question. ML has none before 11-16, so it drops out.
- **Resolution:** document the rule in the API schema and `api.html`, and add a
  `common` block (the same board as home). Do not change the scoring rule.

**F8 · Clean-day rule · S3 / H-low · Clean days depend on the evening run, which the
scheduler misses**
- **Evidence:** 11-16 is not clean ("missing completed workflow work: evening").
- **Risk:** once H20 is done this goes away. Do not weaken the rule (SPEC 2.9 is
  owner-only). Only document it.

**F9 · Base rate worse than 50 % · S4 / H-med (interview question)**
- **Evidence:** rehearsal base rate Brier is 0.305 on 105 questions; persistence is 0.276.
- **Cause:** the Laplace base rate over past instances does not transfer to new
  templates and domains early on.
- **Resolution:** none to the model (I8). Add one sentence on Findings or Methods
  explaining why a base rate can score above 0.25 early, so an interviewer's question has
  a written answer.

**Disproved or already fixed** (do not redo):
- ML not live: fixed by T193 and verified on 4 batches.
- `agent_graph` tool_use 400: fixed.
- Structured-output 100 % errors: fixed.
- Missing attention resolutions on batch 11-17 are not a bug; they resolve after 12:00 UTC
